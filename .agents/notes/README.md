# Agent Notes

Agent Note 是决策与方向的简要记录，保留背景、选择、理由和适用边界。每份围绕一项可独立讨论和判断落实情况的事项。

根目录 `AGENTS.md` 引导按当前任务读取相关 Note。

## 目录与生命周期

```text
{lifecycle}/yyyy-mm-dd-topic-title.md
```

- `proposed/`：方向已提出，尚未落实或只落实了一部分。
- `implemented/`：该项方向已落实，必要验证已完成。
- `rejected/`：该项方向明确不采纳，保留原因。

文件直接放在对应生命周期目录下。文件名日期表示主题首次提出日期，后续更新保留该日期。

生命周期按本项决定的落实情况判断。状态变化时移动原文件，同步状态行及相关引用；进入 `implemented/` 时保留 `Proposal`，在其后新增 `Decision`。

## 何时新增或更新

- 涉及需要长期保留的决策、方向或关键取舍时，在同一次变更中新增或更新 Note；简单更新同步受影响的 README。
- 先搜索相关 Note。同一决定在原文件中更新，将变化整合到对应主题，保留当前有效的结论；`Proposal` 段的改动见下节。
- 可独立讨论和判断是否落实的另一项决定另建 Note；取代旧决定时写明取代关系，并相互链接。

## `Proposal` 是授权段

- `Proposal` 记录用户已确认的方向与约束，每条带理由。Agent 起草，用户确认后生效。
- 改动 `Proposal` 中已有条目先以 diff 提议、经用户确认，见 `AGENTS.md` 文件读写范围；其余章节随实现更新。
- 实现无法按字面满足 `Proposal` 中某一条时，不改写该条、不绕过：另建 proposed Note 记录冲突与拟采用方向，在该条末尾标 `待裁定 → [Note]`。新 Note 进 `implemented/` 时该条标 `已取代 → [Note]`；进 `rejected/` 时该条不变。
- 交付前逐条核对 `Proposal`；实现与某条不符且未标待裁定的，按上一条处理。

## 内容与写法

- 以事项名称组织正文，用短段落或少量要点说明选择、理由和适用边界。具体值仅在本身构成关键决定或适用条件时保留。
- 关联事项的当前信息引用其负责文档；本 Note 保留与自身决定直接相关的依赖和约束。
- 落实情况用简短的关键结论、依据和适用范围说明，保留影响结论的必要局限。
- 只记录有依据的选择与结论；影响方向或边界的未决事项按具体内容命名，标为待确认。
- 本次任务的执行情况、测试计数与编辑检查结果写在任务回复中，不进入仓库。不可逆的外部操作（数据库写入、发送、部署）在 `Verification` 或提交说明中记一行时间与范围。

## 文件格式

基础内容为 `Problem` 和 `Proposal` 或 `Decision`。以下以 `proposed` 为例：

```markdown
# Agent Note: <事项标题>

Status: proposed

## Problem

<背景及需要决定的问题>

## Proposal

<拟采用的方向、关键理由和适用边界>
```

`implemented` 保留 `Proposal`，在其后以 `Decision` 描述已落实的方向，与 `Proposal` 一致时一行说明，不一致时写明差异与理由；本节生效前的 implemented Note 不回改。`rejected` 保留提议，状态行写为 `Status: rejected — <原因>`。

其他章节按实际内容选用，如 `Alternatives considered`、`Risks`、`Consequences`、`Acceptance criteria`、`Verification`、`Related materials`；每节只保留支撑本项决定的必要信息。

## 与相关材料的关系

- `相关材料/需求迭代/{YYYYMMDD-主题}/` 保存项目不拥有的输入（需求表、会议纪要、第三方契约）和人工整理的历史归档，由人维护；Agent 不在其中新建、修改或删除文件。每个主题目录的 README 说明各文件是输入还是归档。
- Agent 以后需要知道的结论必须写在 Note 或代码中，不能只存在于材料。Note 只链接输入材料：单一材料直接链接，同一组多文件需要共同说明时链接该组材料的 README；归档不从 Note 链接。
- Agent 只在用户指定文件或任务明确要求核对来源时读取材料。人发现材料与 Note 冲突时，指示 Agent 核对来源并更新受影响的结论。
