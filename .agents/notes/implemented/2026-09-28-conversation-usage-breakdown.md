# Agent Note: 对话详情的 Token 用量明细

Status: implemented

## Problem

对话详情页原本只有一行「Token · 估算成本 · 助手消息数」，看不出缓存命中情况、成本构成、
上下文如何随会话膨胀，也定位不到哪一轮、哪一次调用最贵。需要决定明细以什么形态展示、
数字与页头的会话总量如何保持一致，以及 Claude 缓存写分档是否纳入估算。

## Proposal

- 明细放在折叠面板里，默认收起，展开状态本机记住。收起时标题行只有一行摘要。
  理由：不打扰只想读对话的场景，一行摘要已能回答「这个会话花了多少」。
- 展开后采用分层精简布局：五张指标卡（总量 / 成本 / 输入 / 输出 / 缓存命中率），均值、
  占比、缓存节省、缓存写分档放在卡片第二行；Token 与成本各一根构成条；一张按调用顺序
  的图；按模型表只在多模型会话出现。理由：四组指标各占一块会臃肿，卡片第二行放派生
  指标不增加块数。
- 每条助手消息显示本次调用的上下文 / 输出 / 成本，悬停看完整拆分；大纲每个用户轮次
  显示本轮 Token 与成本。理由：能定位哪一轮、哪一次调用最贵。
- 计算指标范围：缓存命中率与缓存节省（全部输入按非缓存价计的成本 − 估算成本）、Token
  与成本构成、上下文随调用顺序的变化、均值与占比（平均每次调用上下文、每轮平均成本、
  推理占比、子代理占比）。理由：用户确认的四组指标。
- 面板与页头总量同源：只统计索引归属到本会话的调用；resume/fork 复制进来、已计入原
  会话的调用灰显标注，不计入任何数字。理由：README 承诺各会话之和等于全局总量，明细
  不能与之矛盾。
- 解析 Claude 缓存写的 5 分钟 / 1 小时分档，1 小时档按输入价 ×2 估算，全局统计同步；
  索引缓存 schema 升到 v6，升级后首次启动全量重建一次。理由：1 小时档单价是 5 分钟档
  的 1.6 倍，一律按 5 分钟档会低估成本。

## Decision

已按 Proposal 落实。与示意图的一处差异：调用图把输出作为第四段堆进同一根柱子，不做
「堆叠柱 + 输出折线」的双 y 轴。理由：双轴的刻度对齐是任意的，容易读出不存在的关系；
四段同一单位只需一条轴，上下文膨胀与 compact 发生点仍一眼可见，输出数值在悬停与消息
标签里。用户已确认保持堆叠，不另加独立的输出小图。

数据契约：`ChatMessage.usage` 携带单次调用用量，其 `call_key` 与索引的 `dedup_key` 由
同一函数计算；`ConversationDetail.usage_breakdown` 含 `calls`、`by_model`、`cost_parts`、
`est_cost_no_cache_usd`、`unattributed_calls`，Token 之和等于会话 `usage`；索引在归属时
记录每条唯一事件的归属会话与子代理标记（`UsageOwnership`），详情据此列出调用。

Codex 的 `token_count` 归到它前面最近一条模型输出的消息，跳过工具结果记录（同为
assistant 角色但不是模型输出）；一条消息只保留第一个 count，多余的只留在索引。这是
启发式规则，Codex 事件本身不与消息绑定。

序列色固定四个槽位（缓存读 / 缓存写 / 非缓存输入 / 输出），两种主题分别校验色觉可分
性；颜色跟随类目，不跟随大小或排名。

## Alternatives considered

- 默认展开、只做紧凑摘要卡、两级折叠：讨论中选择折叠加分层布局。
- 在前端按本文件消息求和得到明细：子代理调用不在本文件，fork 复制的调用会重复计入，
  与页头不一致，改为由索引归属驱动。

## Consequences

- 旧记录没有 `cache_creation` 分档对象时全部按 5 分钟档；缓存写多于读时节省为负，界面
  显示「多花」。
- 子代理调用计入总量与按模型表，但不出现在调用图中，图只表示本文件的上下文。

## Verification

合成 fixture 锁定：详情与索引指纹一致、明细之和等于会话总量、每条事件恰好一个归属、
分档截断与分档定价。前端在浏览器中用合成数据渲染 1280 / 420 宽度与浅色 / 深色核对
布局。未在 Tauri 应用内用真实数据验收。
