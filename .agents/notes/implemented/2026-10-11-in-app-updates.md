# Agent Note: 应用内检查更新与一键更新

Status: implemented

## Problem

应用没有自己的服务器，已安装的用户不知道有新版本，只能等作者另行通知后手动下载重装；应用未签名，每次手动安装都要
处理 Gatekeeper / SmartScreen 的拦截。需要决定用户如何得知并安装新版本，以及「应用不联网」的承诺如何调整。

## Proposal

- 用 Tauri 官方更新组件，以本仓库的 GitHub Release 为更新源：发版时生成签名的更新包和清单 `latest.json`，应用读取
  `releases/latest/download/latest.json` 判断有无更高版本，下载后用内置公钥核对签名，再安装并重启。理由：不需要自己的
  服务器；应用自己下载的安装包不再被系统拦截；签名保证只安装作者发布的包。
- 签名密钥由 Agent 在云端会话中生成，私钥和密码交给作者存进仓库 Secret 和密码管理器，会话里的副本随后删除；签名只在
  GitHub Actions 里进行，本机打包不需要私钥；公钥写进应用配置。理由：作者不用在本机操作；私钥和密码会留在对话记录里，
  但只有私钥推送不了更新，还要有本仓库的发版权限。私钥丢失后，已安装的应用再也无法接受更新，只能手动重装。
- 启动后自动检查，每天最多一次，失败不提示；设置里提供「自动检查更新」开关（默认开）和「检查更新」按钮，手动检查失败时
  显示原因，并可打开下载页。理由：默认关闭就等于没有提醒；网络受限时不打扰。
- 发现新版本只在顶栏提示，点开看更新说明，由用户选择「立即更新」。理由：不打断正在看的内容，更不更新由用户决定。
- 联网只用于检查和下载更新：只请求本仓库 GitHub Release 上的文件，不发送历史、路径或统计。各处「不联网」的说明改为
  「除检查更新外不联网，可在设置中关闭」，并写明本机会话 Markdown 里的远程图片会直接加载。理由：隐私说明要与实际行为
  一致。
- 发版时 Release 先建成草稿，所有平台的安装包和清单都上传完再发布。理由：清单由各平台的构建任务分别写入；草稿期间
  固定地址仍指向上一版，用户不会读到只含部分平台的清单。

## Decision

已按 Proposal 落实，实现见开发文档 §16 与发布指南 §5。补充的边界：

- 上次发现的新版本还没安装时，每次启动都会检查，不受每天一次的限制，让顶栏提示一直在。
- 开发构建不安装更新：可执行文件不在应用包里，替换的位置不对。
- 弹窗里的更新说明去掉 Release 正文开头的版本标题和末尾的安装说明。
- 新增依赖：tauri-plugin-updater 2.12.0。

## Consequences

- v0.12.0 及更早的版本没有检查代码，用户要手动升级到第一个带更新功能的版本一次。
- 只接受更高的版本号：发版有问题只能再发一个更高的版本修复，不能回退。
- 仓库须保持公开，删除或改成私有后，已安装的应用无法更新；用户要能访问 GitHub（跟随系统代理）。
- 已发布的版本不能重跑发版工作流，修复要升版本号。

## Verification

- 本机打包验证：带 `tauri.updater.conf.json` 时缺私钥会失败，有私钥时生成的签名能用应用里的公钥核对通过；不带时本机
  打包不需要私钥。签名核对脚本对改动过的文件会拒绝。
- 前端没有单元测试框架；在浏览器中用模拟 IPC 核对：自动检查的时机、开关与每天一次的间隔，顶栏提示，弹窗里的更新说明，
  下载与安装进度，安装失败，设置里的手动检查与打开下载页。
- 真机验证：macOS 上从 v0.13.0 在应用内一键更新到 v0.13.1 已走通；Windows 还没在真机上验证，下次发版时在装着上一版的
  Windows 上更新一次。
- 发版产物核对：v0.13.0、v0.13.1 的 `latest.json` 经应用的固定地址可取到，平台条目齐全，各更新包的签名都能用应用里的
  公钥核对通过。
